# 第7章 現在の本番契約：注意、コンテキスト、キャッシュ

> 本章は 2026-08-03 時点の実行状態を説明します。第1～6章は P1 の設計思想、旧ノード体系、過去の実験を保存するための章です。旧章にある「コンポーネント状態」「AI P1 が現役」「旧ノード番号」が本章と矛盾する場合は、本章と現在のソースコードを正とします。

## 7.1 現在のモード

P1 には三つの有効な状態があり、二つのリコールエンジンは相互排他です。

| 状態 | 自己駆動 P1 | AI P1 | 動作 |
|---|---:|---:|---|
| `00` | オフ | オフ | P1 リコールを実行しない |
| `10` | オン | オフ | ローカル Node0–4 ホワイトボックスリコール。現在の Chat、Code、Work の既定ルート |
| `01` | オフ | オン | 従来の P1AI リコールを保持。現在の Smart、Bot ルート |

`11` の同時有効化は公開していません。ホストは owner を一つだけ選び、二重実行、二重注入、二つのモジュール間の再帰を防ぎます。将来「自己駆動 P1 を先に実行し、その結果をマクロ経由で P1AI に渡す」実験を行う場合も、二つの owner を同時に開くのではなく、独立した一方向パイプラインとして設計する必要があります。

## 7.2 今回の注意入力契約

自己駆動 P1 の Node0 は、次の四種類の単位を厳密に分離します。

```text
user_current：現在のユーザー入力。常に 1 件
user_context：直近のユーザーメッセージ。最大 5 件、新しい順
data：現在のユーザー、キャラクター、モードに属する構造化 Data
ai_output：0 件。過去の AI 返信をリコールのアンカーにしない
```

ここでの Data は、ユーザーが編集・検証できる長期コンテキストです。AI 履歴の後ろに同じ材料をもう一組追加するものではありません。この契約により、ユーザーの最新の意図と、ユーザーが管理する構造化された事実が注意を主導し、過去の AI の言い回しが繰り返し自己強化される可能性を下げます。

「直近 5 件」が制限するのはリコールのアンカーだけです。メインモデルが最終的に 5 件の会話しか見られないという意味ではありません。ホストはウィンドウ、モード、INJ、プリセット、コンテキスト予算に応じてメインプロンプトを組み立てます。P1 は、長期材料のうち今回もう一度見せる価値があるものを決めます。

## 7.3 Node0–4 ホワイトボックスチェーン

```text
Node0  入力のコンパイル
  ├─ 現在のユーザー入力
  ├─ 直近最大 5 件のユーザーコンテキスト
  └─ Data
        ↓
Node1  トークン化、品詞、有効なアンカー
  ├─ 中国語・英語のトークン化/POS
  ├─ 年月日、202x/xx/xx などの時間表現
  └─ 固有名詞とフレーズ
        ↓
Node2  関連の展開
  └─ SWOW / ConceptNet / Cilin / ATOMIC / ドメイン語彙
        ↓
Node3  複数証拠による審査
  └─ BLQ / NB300 / WordNet などの信号で候補を採否
        ↓
Node4  実記録のリコールとランキング
  ├─ Data + hot/warm/cold
  ├─ 現在のウィンドウに対応する Code/Work Markdown
  ├─ 完全一致フレーズ、BM25、明示的な時間、ファイル作成時刻
  └─ レイヤー、Top、pinned、importance、weighted/RRF
        ↓
recalledRecords + directionWords + trace
```

Node2 が生成する関連語は記憶上の事実ではありません。候補は Node3/Node4 で実在する記録へ戻り、証拠確認とランキングを通過してから、はじめてホストのコンテキストへ入れます。

## 7.4 四つの分離次元

実行時のルーティングは、次の四次元を同時に保持します。

1. **ユーザー**：異なるユーザーのデータを混線させない。
2. **キャラクターカード**：同じユーザーでもキャラクターごとに記憶ソースを分ける。
3. **chatId**：主に Code の複数ウィンドウで会話の所有先を維持する。
4. **ウィンドウ/モード**：現在の Chat、Code、Work ウィンドウごとに、選択、短期状態、最終ランキングを分離する。

永続ソースと今回だけの可変状態は別物です。メモリ使用量を抑えるため、物理ソースのキャッシュはユーザー × キャラクター × モードで共有できます。chatId やウィンドウごとにファイルキャッシュ全体を複製する必要はありません。ただし今回の入力、候補集合、最終順位、注入結果は chatId/ウィンドウの所有先を保持し、共有キャッシュから動的な結果をそのまま再利用してはいけません。

## 7.5 Data、三層記憶、ファイル時刻

- **Data**：構造化され、ユーザーが編集できる状態と長期的事実。P1 の入力であり検索ソースでもある。
- **hot**：最近、高頻度、現在使用中の材料。
- **warm**：現在の段階に属するアーカイブ材料。
- **cold**：必要に応じて呼び戻せる長期履歴。
- **Code/Work Markdown**：現在のウィンドウとモードに応じてソース集合へ入り、重要な内容を `data/` だけに保存する必要はない。

時間は本文中の文字列一致だけではありません。明示された年月日、標準日付、記録時刻、ファイル作成時刻も候補の信号になります。時間一致は注目度を上げますが、テキスト証拠、レイヤー、重要度と一緒に順位付けされます。「新しいファイル」という理由だけで、本当に関連する記録を上回ることはありません。

Top も一般的な検索の `top_k` ではありません。pinned/top、importance、recency、レイヤー、過去のヒットなど、材料を再び注意の近くへ動かす永続信号の集合です。ユーザーがこれらの値を変更すると、ソースのバージョンが失効し、インデックスが再構築されます。

## 7.6 P1 キャッシュ契約

### 7.6.1 物理ソースキャッシュ

`storage_read.mjs` は JSON、JSONL、Markdown を再帰的に読み、ファイルの mtime、birthtime、size からバージョン署名を生成します。キャッシュヒット時はディスク読み込みと解析を省略し、ファイル変更時は再構築します。LRU の既定値およびハード上限は 8 スコープです。

キャッシュキーは、共有可能なユーザー × キャラクター × モードの物理ソースを表します。chatId/ウィンドウの可変状態は複製しません。

### 7.6.2 トークン化・POS キャッシュ

`node1_tokenize.mjs` は、完全なテキスト、トークン化/POS バックエンド、リソース識別子からキーを作ります。完全な契約検証に合格した結果だけをキャッシュし、失敗、欠落フィールド、途中結果はキャッシュしません。読み書き時にオブジェクトを複製し、下流の変更が後続リクエストを汚染することを防ぎます。既定容量は 4096、ハード上限は 16384 です。

### 7.6.3 転置インデックスキャッシュ

`node4_rank.mjs` がキャッシュするのは純粋な `docs → postings` インデックスだけです。バージョンは本文、メタデータ、ファイル時刻、Top、importance などランキングに影響する材料を含み、変更時に再構築します。候補集合、クエリ重み、最終ウィンドウランキングを共有結果としてキャッシュすることはありません。インデックス LRU のハード上限は 8 で、文書トークンキャッシュにも容量制限があります。

### 7.6.4 リソースとサービスのライフサイクル

- NB300 は `mmap_mode="r"` を使い、ベクトル行列全体を一度にメモリへ複製しません。
- tokenizer、ONNX POS、任意リソースは必要時に読み込みます。
- tokenize/vector/llmtok の三つの HTTP サービスは常駐し、メッセージごとに spawn しません。
- warmup は single-flight で、同時に一回だけ実行します。
- 短いアイドル時間では既定で自動終了せず、次のリクエストで約 20 秒のコールドスタートを繰り返すことを避けます。必要ならアイドル終了を設定できます。

設計原則は、**安定ソースを共有し、中間生成物をバージョン化し、今回の状態を分離し、失敗をキャッシュしない**ことです。

## 7.7 メインモデルのプロンプトキャッシュ

P1 キャッシュは検索側の重複計算を減らし、プロンプトキャッシュはメインモデルの安定した接頭部に対する重複課金を減らします。両者は別の層です。

Anthropic 互換ルートでは：

- 第1ブレークポイントを安定した system 領域に置く。
- 第2ブレークポイントを動的な Data、after-chat など変化しやすい末尾の手前に置く。
- 古いツール結果を累積サイズに応じて圧縮し、最近の完全な詳細を残す。
- 200k token 未満では、既定で AI が不用意に `<contextClean>` を実行しないようにし、安定した接頭部の頻繁な書き換えを避ける。
- ユーザーの原文メッセージを保護する。通常の整理は復元可能な非表示で、完全削除には明示操作が必要。

対応する prompt caching 契約を持つプロバイダールートだけにブレークポイントを適用します。他のモデルへ同じ削減率をそのまま適用することはできません。

## 7.8 ホワイトボックス証拠と不具合の兆候

検証可能な P1 実行記録には、少なくとも次が必要です。

- 元入力が Node0 に入り、中国語が UTF-8 のままか。
- `user_current/user_context/data/ai_output` の単位数。
- Node1 が実際に token、POS、時間、固有名詞アンカーを生成したか。
- Node2/3 の各経路で候補が何件入り、何件除外され、なぜ失敗したか。
- Node4 の走査文書数、index cache hit/rebuilt、ランキング信号、最終ソース。
- モデル、リソース、HTTP、タイムアウト、メモリのエラーを明示し、黙って「0 件リコール」に変換しないこと。

P9 フィードバックは `p1_feedback_v1` 構造化パケットで trace、候補、ヒット、所要時間、ユーザーフィードバックを記録します。P9/CLI は語彙保守や後の微調整に利用できますが、一度「リコールされなかった」だけで単語をグローバル辞書へ自動追加してはいけません。出典、スコープ、変更案、人による確認が必要です。

## 7.9 現在の実測境界

2026-08-03 のテストマシンにおけるバックエンドのホワイトボックス記録では、中国語のヒット要求は約 `560.9 ms`、71 文書を走査し 1 件を返しました。最初のヒットなし要求は約 `1157 ms` でした。同日後の完全なプロセスツリー計測ではワーキングセットのピークが約 `2054.5 MiB` となり、厳格な 2048 MiB ゲートを約 6.5 MiB（約 0.32%）超えたため、厳格な 2 GiB 合格条件は未達です。この結果は以前の 1.72 GB 観測を置き換えます。

これは現在のバックエンド伝達と中国語経路が一通り動作することを示しますが、安定したベンチマークではありません。公開可能な評価には、cold/warm の複数回測定、P50/P95、ピークメモリ、gold record 付き Recall@k、MRR、nDCG、失敗例が必要です。gold のない過去の四モードサンプルを「リコール率 90%」と宣伝してはいけません。

## 7.10 チーム記憶製品との位置づけの違い

TencentDB Agent Memory にもコンテキスト予算とキャッシュ設計があります。L2/L3 は直接注入でき、L0/L1 はツールとして読めます。Fixed Binding と ACL でスコープを制限し、MemoryProxy は session、injection、skill 状態をキャッシュします。複数ノードでは上流 KV cache miss を避けるため共有ストレージが必要です。

北麓は、相手に「コンテキストやキャッシュがない」と主張すべきではありません。より正確な違いは、TencentDB が主に Agent の持ち運べるチーム記憶資産を管理するのに対し、北麓は長期対話の各ターンで、モデルが何に注意し、どの証拠で順位付けし、プロンプトのどこへ置くかをコンパイルし、動的な注意を固定せずに安定計算だけを有界キャッシュで再利用する点です。
