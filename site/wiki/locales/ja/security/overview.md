# セキュリティセンター

[設定 → セキュリティセンター](beilu:settings/security)でセキュリティ状態を確認し、セキュリティポリシーを管理します。

## クイック操作

1. [セキュリティセンター](beilu:settings/security)パネルを開きます
2. パネル上部の**セキュリティサマリー**を確認し、現在のセキュリティ状態を把握します
3. **ワンクリックセキュリティチェック**をクリックし、すべてのチェック項目をスキャンして結果を集約します
4. チェック項目リストで各項目を確認し、セキュリティポリシーを調整します

### パネルコントロール一覧

| コントロール | 説明 |
|------|------|
| セキュリティサマリー | パネル上部に現在のセキュリティ状態の概要を表示します |
| ワンクリックセキュリティチェック | ボタン。すべてのチェック項目をスキャンして結果を集約します |
| チェック項目リスト | チェック項目のタイプに応じて異なるコントロール（ドロップダウン / スイッチ / EJS 設定 / リスト）を動的にレンダリングし、各項目の確認と調整に使用します |
| コンテンツフィルタ — ブラックリストキーワード | テキスト入力。フィルタリングするキーワードを設定します |
| コンテンツフィルタ — ユーザー名フィルタ | テキスト入力。フィルタリングするユーザー名を設定します |
| iframe セキュリティレベル | 3 段階から選択。iframe 埋め込みの制限レベルを制御します |

チェック項目リストの各項目は具体的なセキュリティポリシー（デプロイモード、コマンド実行、サンドボックス設定など）に対応しており、owner はここで集中管理でき、個別にプラグイン設定に入る必要がありません。

## デプロイモードの切り替え

always-accompany は2つのデプロイモードを区別し、セキュリティポリシーはそれに応じて調整されます：

### local モード（デフォルト）

個人のローカル使用に適しています。セキュリティポリシーは比較的緩やかです：

- ファイル操作はデフォルトでワークスペース内で許可
- コマンド実行はデフォルトで許可
- シンボリックリンクの実パス検証は行いません
- 唯一のユーザーが owner となります

### server モード

マルチユーザー共有デプロイに適しています。セキュリティポリシーが厳格化されます：

- コマンド実行はデフォルトで無効。owner が明示的に有効にする必要があります
- シンボリックリンクの実パス検証を実施（シンボリックリンクを利用した脱出を防止）
- セキュリティ関連設定の書き込みには owner 権限が必要
- 無効なデプロイモード値は server にフォールバック（fail-safe）

環境変数 `BEILU_DEPLOY_MODE=server` またはセキュリティセンターパネルの `config.deployMode` で切り替えます。

## プラグインセキュリティ設定の管理

以下のプラグイン設定の変更には owner 権限が必要です（[プラグイン管理](beilu:settings/plugins)パネルで設定）：

| プラグイン | センシティブな設定 | リスク |
|------|---------|------|
| beilu-files | allowExec / rootPath / workspaceRoot | コマンド実行の有効化 / サンドボックス境界の変更 |
| beilu-ejs | sandboxOptOut | EJS サンドボックスの無効化 |
| beilu-regex | regexGuard | ReDoS 保護の無効化 |

これらの設定の書き込みは parts_router の config/setdata エントリで統一的にインターセプトされ（`partConfigWriteNeedsOwner`）、各プラグイン内部で個別にインターセプトされるのではありません。

## 3 つのコア原則

1. **セキュアデフォルト**：すべてのセキュリティスイッチはデフォルトで最も安全な状態にあり、高リスク機能は能動的に有効にする必要があります
2. **Owner 制御**：セキュリティポリシーはインスタンスの owner が管理し、一般ユーザーはセキュリティ関連設定を変更できません
3. **多層防御**：各セキュリティドメイン（パス/ネットワーク/実行/認証）に複数の防御層があり、1層が突破されても全面的な侵害にはつながりません

## セキュリティアーキテクチャ概要

| セキュリティドメイン | コア機構 | 保護対象 |
|--------|---------|---------|
| 認証・認可 | JWT + API Key + ブルートフォース防御 | ユーザーアイデンティティ |
| パスフェンス | confinePath + confineSegment | ファイルシステム |
| 会話帰属 | router.param("chatid") による中央検証 | 会話データ |
| コンテンツセキュリティ | CSP + WS Origin 検証 | フロントエンドセキュリティ |
| 実行ゲート | deployGatedAllow | コマンド実行 |
| プラグインセキュリティ | partConfigWriteNeedsOwner | プラグイン設定 |
| トークンゲート | pet-token 認証 | スクリーンショットインジェクション |

## ファイル操作セキュリティ

beilu-files の4層多層防御：

1. **パス正規化**：`..`、絶対パスインジェクションを処理し、パスをワークスペースにアンカリング
2. **システムパス遮断**：システムのセンシティブなディレクトリとファイルへのアクセスを阻止
3. **ワークスペースサンドボックス**：すべての操作は workspaceRoot 内で行われる必要があります
4. **ホワイトリスト/ブラックリスト**：きめ細かいパス制御

詳しくは [ファイル操作 (beilu-files)](../plugins/files.md) をご覧ください。[プラグイン管理](beilu:settings/plugins)パネルで設定できます。

## 会話データの保護

### 帰属検証

`:chatid` をパスパラメータとするすべてのエンドポイントは、`router.param("chatid")` による中央帰属検証を実施——リクエストユーザーがその会話の owner であるかを検証します。検証に通らないリクエストは 403 を返します。

### Body 内の chatid

一部のエンドポイントはリクエストボディで chatid を渡します（manual-tool-call、group bind、branch など）。これらのエンドポイントには独立したインライン検証ロジックがあります。

## ネットワークセキュリティ

- **CSP（コンテンツセキュリティポリシー）**：実装済み。読み込み可能なリソースのソースを制限します
- **WS Origin 検証**：WebSocket 接続時に Origin ヘッダーを検証し、クロスサイト WebSocket ハイジャックを防止します
- **safeFetch**：ネットワークリクエストはセキュアフェッチ関数を通じて行われ、タイムアウトと悪意のある URL フィルタリングが組み込まれています

## マルチユーザー分離

server モードでは、always-accompany は以下のデータについてユーザーレベルの分離を行います：

- 会話データとチャット履歴
- プリセット設定とプリセットファイル
- プラグイン設定（AsyncLocalStorage による per-user 分離）
- ファイル操作のワークスペース設定
- 記憶システムデータ
