# 第7章 目前生產契約：注意力、上下文與快取

> 本章說明截至 2026-08-03 的目前執行狀態。第1–6章保留 P1 的設計理念、舊節點體系與歷史實驗；當歷史章節中的「組件態」、「AI P1 現役」或舊節點編號與本章衝突時，以本章和目前原始碼為準。

## 7.1 目前模式

P1 有三種有效狀態，兩個召回器互斥：

| 狀態 | 自驅動 P1 | AI P1 | 行為 |
|---|---:|---:|---|
| `00` | 關 | 關 | 不執行 P1 召回 |
| `10` | 開 | 關 | 本機 Node0–4 白盒召回；目前 Chat、Code、Work 的預設路由 |
| `01` | 關 | 開 | 保留原 P1AI 召回；目前 Smart、Bot 的路由 |

目前不開放 `11` 雙開。宿主只裁決一個 owner，避免雙跑、雙注入和兩個模組互相遞迴。若後續實驗「自驅動 P1 先跑，結果經巨集交給 P1AI 再處理」，也應設計成獨立的單向組合管線，不能同時開啟兩個 owner。

## 7.2 本輪注意力輸入契約

自驅動 P1 的 Node0 嚴格區分四類單元：

```text
user_current：目前使用者輸入，固定 1 條
user_context：最近使用者訊息，最多 5 條，由近到遠
data：目前使用者、角色與模式的結構化 Data
ai_output：0 條；不把歷史 AI 回覆當成召回錨點
```

Data 在這裡是可編輯、可驗證的長期上下文，不是附在 AI 歷史後面的第四份重複材料。這個契約讓使用者的最新意圖與使用者維護的結構化事實主導注意力，降低舊 AI 措辭被系統反覆自我強化的機會。

「最近 5 條」只限制召回錨點，不代表主模型最後只能看見 5 條對話。宿主仍可依視窗、模式、INJ、預設與上下文預算組裝主提示詞；P1 只負責決定長期材料中哪些內容值得在本輪重新出現。

## 7.3 Node0–4 白盒鏈

```text
Node0  輸入編譯
  ├─ 目前使用者輸入
  ├─ 最近 5 條使用者上下文
  └─ Data
        ↓
Node1  斷詞、詞性、有效錨點
  ├─ 中文與英文斷詞/POS
  ├─ 時間表達：年、月、日、202x/xx/xx 等
  └─ 專有名詞與片語
        ↓
Node2  關聯擴展
  └─ SWOW / ConceptNet / 詞林 / ATOMIC / 領域詞
        ↓
Node3  多證據審查
  └─ BLQ / NB300 / WordNet 等訊號決定候選去留
        ↓
Node4  真實記錄召回與排序
  ├─ Data + hot/warm/cold
  ├─ 與目前視窗對齊的 Code/Work Markdown
  ├─ 精確片語、BM25、時間與檔案建立時間
  └─ 層級、Top、pinned、importance、weighted/RRF
        ↓
recalledRecords + directionWords + trace
```

Node2 的聯想不是記憶事實。候選必須在 Node3/Node4 回到真實記錄層接受證據與排序，最終輸出才可以進入宿主上下文。

## 7.4 四個隔離維度

執行時路由需要同時攜帶：

1. **使用者**：不同使用者的資料不能串線；
2. **角色卡**：同一使用者的不同角色擁有不同記憶來源；
3. **chatId**：主要維持 Code 多視窗的對話綁定與穿透；
4. **視窗/模式**：目前 Chat、Code、Work 視窗的選擇、短期狀態與最終排序彼此獨立。

持久化來源和本輪可變狀態不是同一件事。為了節省記憶體，實體來源快取可以按使用者 × 角色 × 模式共享；不需要為每個 chatId 和視窗複製完整檔案快取。但本輪輸入、候選、最終排名和注入結果必須保留 chatId/視窗歸屬，不能直接重用共享快取中的動態結果。

## 7.5 Data、三層記憶與檔案時間

- **Data**：結構化、使用者可編輯的狀態與長期事實，也是 P1 的輸入與檢索來源；
- **hot**：近期、高頻、正在使用的材料；
- **warm**：階段性封存材料；
- **cold**：長期歷史，仍可按需召回；
- **Code/Work Markdown**：依目前視窗與模式選入來源集合，不要求唯一重要內容都放在 `data/` 目錄。

時間不只從正文做字串比對。明確年月日、標準日期、記錄時間和檔案建立時間都可成為候選訊號。時間符合會獲得更高關注，但仍要與文字證據、層級和重要度一起排序，不能只因為「檔案較新」就壓過真正相關的記錄。

Top 也不等於一般搜尋的 `top_k`。它是一組能讓材料重新靠近注意力的持久訊號，包括 pinned/top、importance、recency、層級與歷史命中。使用者修改這些值後，來源版本會失效並重建索引。

## 7.6 P1 快取契約

### 7.6.1 實體來源快取

`storage_read.mjs` 遞迴讀取 JSON、JSONL、Markdown，並以檔案 mtime、birthtime、size 產生版本簽章。命中快取時跳過磁碟讀取與解析；檔案變更時重建。LRU 預設與硬上限都是 8 個作用域。

快取鍵面向可共享的使用者 × 角色 × 模式實體來源，不複製 chatId/視窗可變狀態。

### 7.6.2 斷詞與 POS 快取

`node1_tokenize.mjs` 以完整文字、斷詞/POS 後端與資源身分組成鍵。只有通過完整契約驗證的結果才能進入快取；失敗、缺少欄位或半成品不快取。讀寫都複製物件，避免下游修改污染後續請求。預設容量 4096，硬上限 16384。

### 7.6.3 倒排索引快取

`node4_rank.mjs` 只快取純 `docs → postings` 索引。版本涵蓋正文、後設資料、檔案時間、Top、importance 等影響排序的材料；變更後重建。候選集合、查詢權重和最終視窗排名從不作為共享結果快取。索引 LRU 硬上限為 8，文件斷詞快取也有容量修剪。

### 7.6.4 資源與服務生命週期

- NB300 使用 `mmap_mode="r"`，避免一次把完整向量矩陣複製進記憶體；
- tokenizer、ONNX POS 與可選資源按需載入；
- tokenize/vector/llmtok 三個 HTTP 服務常駐，不在每則訊息上 spawn；
- warmup 使用 single-flight，同一時間只執行一次；
- 預設不因短暫閒置自動關閉，避免下一輪重新承擔約 20 秒冷啟動；需要時仍可設定閒置退出。

設計原則是：**共享穩定來源、版本化中間產物、隔離本輪狀態、失敗不進快取。**

## 7.7 主模型提示詞快取

P1 快取減少檢索側重複計算；提示詞快取減少主模型穩定前綴的重複計費，兩者不能混為一談。

在 Anthropic 相容路徑中：

- 第一斷點位於穩定 system 區；
- 第二斷點位於動態 Data、after-chat 等易變尾部之前；
- 舊工具結果依累計體積動態壓縮，保留最近的完整細節；
- 預設低於 200k token 時阻止 AI 隨意執行 `<contextClean>`，避免頻繁改寫穩定前綴；
- 使用者原始訊息受保護，清理預設為可復原隱藏，永久刪除必須明確執行。

只有支援對應 prompt caching 的供應商路徑才套用這些快取斷點；其他模型不能沿用相同的收益口徑。

## 7.8 白盒證據與 Bug 訊號

一次可交付的 P1 執行記錄至少應顯示：

- 原始輸入是否進入 Node0，中文是否維持 UTF-8；
- `user_current/user_context/data/ai_output` 各有多少單元；
- Node1 是否真的產生 token、POS、時間與專名錨點；
- Node2/3 每類候選的進入、刪除與失敗原因；
- Node4 掃描文件數、索引 cache hit/rebuilt、排名訊號與最終來源；
- 模型、資源、HTTP、逾時與記憶體錯誤必須明確回報，不能靜默變成「0 條召回」。

P9 回饋使用 `p1_feedback_v1` 結構化封包記錄 trace、候選、命中、耗時和使用者回饋。P9/CLI 可以據此維護詞庫或進行後期微調，但不能因一次使用者「沒召回」就自動把詞寫進全域詞庫；仍需保留來源、作用域、建議變更與人工確認。

## 7.9 目前實測邊界

2026-08-03 目前機器的後端白盒記錄：中文命中請求約 `560.9 ms`，掃描 71 份文件、回傳 1 條；第一次無命中請求約 `1157 ms`。同日稍後一次完整處理程序樹的工作集峰值約 `2054.5 MiB`，高於 2048 MiB 嚴格門檻約 6.5 MiB（約 0.32%），因此嚴格 2 GiB 驗收未通過；較早的 1.72 GB 記錄已被這次實測取代。

這證明目前後端傳導與中文鏈路可以跑通，但不是穩定效能基準。正式發布前仍需要多輪 cold、warm、P50、P95、記憶體峰值，以及帶 gold record 的 Recall@k、MRR、nDCG 與失敗案例。現階段不能把歷史上沒有 gold 的四模式樣本宣傳成「召回 90%」。

## 7.10 與團隊記憶產品的定位差異

TencentDB Agent Memory 同樣具備上下文預算和快取設計：L2/L3 可直接注入，L0/L1 可透過工具讀取，Fixed Binding 與 ACL 限制作用域；MemoryProxy 會快取 session、injection 和 skill 狀態，多節點部署也需要共享儲存，避免上游 KV cache miss。

北麓不應聲稱對方「沒有上下文或快取」。更準確的差異是：TencentDB 主要管理 Agent 可攜帶的團隊記憶資產；北麓主要在長期對話的每一輪編譯模型應注意什麼、按哪些證據排序、放到提示詞哪裡，並以有界快取重用穩定計算而不凍結動態注意力。
