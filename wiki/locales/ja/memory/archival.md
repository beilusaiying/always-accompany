# 記憶アーカイブと検索

記憶アーカイブは記憶システムの「新陳代謝」です——アクティブでなくなった記憶をホットレイヤーから warm 層や cold 層に自動的に移行し、同時にリコールエンジンが必要時に関連記憶を呼び戻す仕組みを提供します。これにより、ホットレイヤーが無限に膨張することなく、過去の記憶も本当に失われることはありません。

## 三層移行パス

```
hot（ホットレイヤー）
  ↓ 自動移行（エントリのエイジング/容量管理）
warm（ウォーム層）
  ↓ さらにエイジング
cold（コールド層/アーカイブ）
```

### hot → warm 移行

トリガー条件：
- 記憶エントリが一定期間アクセスされていない
- ホットレイヤーの総容量が上限に近づいている
- P2 の要約アーカイブ後、元の詳細エントリが降温される

移行後、エントリは毎ターンの自動インジェクションから**オンデマンドリコール**に変わります。

### warm → cold 移行

トリガー条件：
- ウォーム層のエントリがさらにエイジングし、長期間リコールされていない
- ウォーム層の容量管理が必要

移行後、エントリは長期アーカイブに入り、**手動検索**でのみ到達可能になります。

## 移行の例外

以下の内容は**移行の対象外**であり、常にホットレイヤーに残ります：

- `forever.json` 内の永久記憶
- 現在アクティブなテーブルエントリ（使用中のテーブル行）
- システムレベルの設定情報

## リコールエンジン

リコールエンジンは P1 自律パイプラインのコアコンポーネントであり、warm/cold 層から現在の会話に関連する記憶エントリを見つけてコンテキストに取り込む役割を担います。

### リコールフロー

```
ユーザーがメッセージを送信
    ↓
NLP 分かち書き：ユーザーメッセージからキーワードを抽出
    ↓
連想拡張：キーワードに対する意味的連想を実行
    例："雨" → "雨、天気、傘、濡れる、湿気"
    ↓
マルチワード共起マッチング：warm/cold 層を検索
    - 複数のキーワード/連想語を同時に含むエントリを検索
    - マルチワード共起は単語単体マッチングより精度が高い
    ↓
4 次元スコアリング（各候補エントリに対して）：
    ↓
ソートして top-N エントリを取得
    ↓
今回のコンテキストにインジェクション
```

### 4 次元スコアリングの詳細

| 次元 | 評価内容 | 説明 |
|------|----------|------|
| **semantic** | 意味的関連度 | エントリの内容と現在のトピックの意味的マッチング度合い |
| **lexical** | 語彙マッチ度 | キーワードの直接的なテキストマッチング、精度が高い |
| **recency** | 時間近接度 | 新しい記憶ほどスコアが高く、「最近のことほど思い出しやすい」を体現 |
| **importance** | 重要度 | 重要とマークされた記憶はスコアが高く、優先度を体現 |

4 つの次元でそれぞれスコアを計算した後、加重合計してソートします。ウェイト設定は調整可能です。

### マルチワード共起

マルチワード共起はリコール精度の鍵となるメカニズムです。単一キーワードのマッチングでは大量の無関係なエントリがリコールされますが、複数のキーワードが同時にエントリに含まれることを要求することで、関連性を大幅に向上させます：

- ユーザーが「前回公園で会ったあの猫」と言う → キーワード「公園」「猫」を抽出
- 「公園」のみを含むエントリや「猫」のみを含むエントリは優先的にリコールされない
- 「公園」と「猫」を同時に含むエントリが高スコアを獲得

## スナップショット管理

[記憶管理](beilu:mode/memory)のツールバーで **snapshot** ボタンをクリックするか、記憶メンテナンスエリアで「スナップショット」サブ Tab に切り替えると、記憶スナップショットを管理できます。

スナップショットは 2 種類あります：

### 記憶スナップショット

- **作成**：作成ボタンをクリックし、今回のスナップショットの目的を説明するメモを付けることができます
- **復元**：スナップショットリストから 1 つ選択し、確認（confirm）すると、そのスナップショット時点の記憶状態に復元されます
- **一覧**：作成済みのすべての記憶スナップショットを時間の新しい順に表示します

### Git スナップショット

- **作成**：作成ボタンをクリックし、label をタグ識別子として入力します
- **復元**：Git スナップショットを 1 つ選択して復元します。システムは復元前に自動的に pre-restore の保険用スナップショットを作成し、誤操作によるデータ損失を防ぎます
- **一覧**：作成済みのすべての Git スナップショットを時間の新しい順に表示します

## アーカイブツールバー

[記憶管理](beilu:mode/memory)のファイルブラウザで、上部のアーカイブツールバーが以下の一括操作を提供します：

| 操作 | 説明 |
|------|------|
| 一時記憶のアーカイブ | 一時記憶エントリをホットレイヤーから warm 層に移行します |
| 当日終了 | その日の締めくくりアーカイブ処理を実行します |
| Hot → Warm | 選択したホットレイヤーのエントリを手動で warm 層に移行します |
| Warm → Cold | 選択した warm 層のエントリを手動で cold 層に移行します |
| 完了タスクのアーカイブ | 完了済みとマークされたタスク記憶をアーカイブします |

これらの操作は自動移行メカニズムの手動補完であり、記憶層の即時整理が必要なシーンに適しています。

## 検索設定

[記憶管理](beilu:mode/memory)のツールバーで **retrieval** ボタンをクリックするか、検索/診断エリアで「検索」サブ Tab に切り替えると、リコールエンジンの動作パラメータを調整できます：

- **P1 自動トリガー toggle**：毎ターンの会話前に P1 が自動リコールを行うかのオン/オフ
- **引用チャット件数**：リコール時に参照する直近のチャットターン数（モード別に独立設定）
- **最大検索ラウンド数**：P1 マルチラウンド検索の上限
- **タイムアウト**：検索のタイムアウト時間設定

## フォーマットチェック

[記憶管理](beilu:mode/memory)のツールバーで **format** ボタンをクリックするか、記憶メンテナンスエリアで「フォーマット」サブ Tab に切り替えると、記憶ファイルのフォーマット準拠チェックを行えます。

- **スキャン**：スキャンボタンをクリックしてチェックを開始
- **集計**：適合 / 警告 / エラー / 合計の 4 項目のカウントを表示
- **ファイル別集計**：各ファイルのチェック結果を個別に表示
- **問題リスト**：最初の 20 件のフォーマット問題の詳細を表示
- **ワンクリックアップグレード**：自動修正可能なフォーマット問題に対して一括アップグレードを実行

## ユーザーへの影響

- アーカイブとリコールはすべて自動で行われ、ユーザーが手動操作する必要はありません
- AI があることを「忘れた」場合、その記憶が cold 層に移行済みでリコールエンジンにトリガーされなかった可能性があります
- 会話中に関連するキーワードを言及することで、リコールエンジンが cold 層の関連記憶を見つけやすくなります
- 特に重要な情報は AI に「永遠に覚えて」とマークさせることをお勧めします。forever.json に入り移行の対象外となります

## 開発者向け説明

- 移行の時間閾値と容量閾値は設定で調整可能です
- リコールの top-N 件数はコンテキストの使用量に影響するため、リコール品質とコンテキストスペースのバランスを取る必要があります
- 4 次元スコアリングのウェイトは実際の効果に応じて調整できます
- 連想拡張の品質はリコールカバレッジに直接影響し、リコール性能のボトルネックの一つです
- cold 層ストレージには容量制限がありませんが、検索パフォーマンスには注意が必要です
