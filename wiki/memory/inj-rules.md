# INJ规则配置

各条 INJ 规则的字段定义、门控逻辑和互斥关系。编辑入口：[注入编辑器](beilu:editor/inj-edit)。

## INJ 规则字段说明

每条 INJ 规则由以下字段定义：

| 字段 | 类型 | 说明 |
|------|------|------|
| **id** | 字符串 | 条目唯一标识（如 INJ-1-chat），互斥变体的配对也按 id 判定 |
| **content** | 字符串 | 注入的内容模板，支持 `{{macro}}` 宏替换 |
| **autoMode** | 枚举 | 门控模式：chat/code/work/bot/smart/always/all/manual/file（另可为自定义模式的域名）。保存时会校验，非法值直接拒绝 |
| **depth** | 数字 | 注入深度：999=系统级, 0=最新消息后, N=第N轮前 |
| **role** | 枚举 | 消息角色：system/user/assistant |
| **enabled** | 布尔 | 是否启用 |
| **platform** | 字符串（可选） | 平台限定：填了只在对应 Bot 平台会话注入；网页对话没有平台标识，带 platform 的条目在网页对话一律不注入 |

## 默认 INJ 规则详解

### INJ-1-chat

- **autoMode**: `chat`
- **depth**: `999`（系统提示级）
- **role**: `system`
- **功能**: 向 AI 说明 chat 模式下的记忆表格系统。内容包括 #0-#9 各表的名称、存储内容、写入格式，以及 `<tableEdit>` 标签的语法说明。

**运行链**: 用户处于 chat 模式 → autoMode 匹配 → INJ-1-chat 的 content 作为 system 消息注入到上下文最前端（depth 999）→ AI 知道如何使用记忆表格。

### INJ-1-write-code

- **autoMode**: `code`
- **depth**: `999`
- **role**: `system`
- **功能**: 向 AI 说明 code 模式下的记忆表格系统。内容包括 C0-C5 各表的名称、存储内容、写入格式。

### INJ-1-work

- **autoMode**: `work`
- **depth**: `999`
- **role**: `system`
- **功能**: 向 AI 说明 work 模式下的记忆表格系统。内容包括 W0-W4 各表的名称、存储内容、写入格式。

### INJ-2

- **autoMode**: `file`（由文件层配置决定）
- **depth**: 可配置
- **role**: `system`
- **功能**: 注入来自角色文件或预设的额外 AI 提示词。这些提示词可能包含角色专属的行为指导、写作风格要求等。

**互斥**: 当 IDE 连接时，系统使用 INJ-2-code 变体替代 INJ-2。两者不会同时生效。

### INJ-3

- **autoMode**: `bot`
- **depth**: 可配置
- **role**: `system`
- **功能**: 注入 Bot 平台（如 Telegram、Discord）的专用提示词。包括平台特定的交互规则、消息格式限制等。

## autoMode 门控逻辑

门控不是一串 if 分支，而是一次"集合成员"判定：系统先根据当前环境算出**本轮接受的注入域集合**，然后看每条 INJ 的 autoMode 在不在集合里。

```
收到消息，识别当前环境（工作模式 / 是否文件模式 / IDE 是否连接 / Bot 平台）
    ↓
算出接受域集合 = {always, all, manual}
    + file（仅文件/IDE 模式时加入；当前实况 = code 模式）
    + 当前模式自己声明的域（如 chat 模式 = {chat, airp}；smart 模式 = {smart, chat, airp}）
    ↓
对每条 INJ 依次过四道闸：
  1. enabled 开着？
  2. autoMode 在接受域集合里？（拼错的值不在任何集合 = 拒绝）
  3. platform 匹配？（没填 = 不限）
  4. 没被互斥规则禁用？
    ↓
四道闸全过 → 执行宏替换 → 按 depth 放入上下文
（例外：注入坞「⚡这轮」点名的条目跳过全部四道闸，本轮直接注入）
```

这样设计的好处：加一个新模式或别名域，只是让集合变大，不需要改任何判定逻辑。自定义模式可以在模式定义里声明自己接受哪些注入域。

## depth 与上下文位置

depth 值决定注入在上下文中的物理位置。理解 depth 需要先理解上下文的结构：

```
[depth 999] 系统提示区域
  ├─ 角色设定
  ├─ INJ-1 表格说明（depth 999）
  └─ 其他系统级 INJ
    ...
[depth N] 聊天历史区域
  ├─ 第 N 轮对话
  ├─ ...（世界书 atDepth 条目在此插入）
  ├─ 第 2 轮对话
  ├─ 第 1 轮对话
[depth 0] 最新消息区域
  └─ 用户的最新消息
```

depth 值越大越靠前（系统级），越小越靠近最新消息。

## 互斥规则详解

### INJ-1 系列互斥

三条 INJ-1（chat / write-code / work）通过 autoMode 自然互斥——同一时刻只有一种工作模式，因此只有一条 INJ-1 的 autoMode 会匹配。

### INJ-2 vs INJ-2-code（变体对互斥三规则）

INJ-2 和 INJ-2-code 是同一位置的两个变体，由三条规则决定谁生效：

1. **IDE 连接 + code 模式 + 变体开启**（且基础版不是手动模式）→ INJ-2-code 生效，INJ-2 自动让位
2. **IDE 未连接** → INJ-2-code 自动禁用，INJ-2 可用
3. **用户手动开启基础版**（INJ-2 设为 manual 且开启）→ 变体禁用，尊重手动选择

两条补充说明：

- **"IDE 连接"指 YonBan 真 IDE（VS Code / Cursor）接入**。CLI 常驻后端连接不算——否则 CLI 随系统自启动会让 INJ-2 永远被变体覆盖。只开 CLI 时生效的是 INJ-2（含完整 CLI 指令段）。
- **变体的判定是按 id 命名配对的**：id 以 `-code`（或 `-chat`/`-work`）结尾、且去掉后缀后的基础版 id 真实存在，才算变体对。比如 INJ-1-write-code 没有对应的 "INJ-1-write" 条目，所以它不是变体，不参与互斥。

## 宏替换详解

宏在 INJ content 中以 `{{宏名}}` 格式书写，注入时被替换为实际值。

**常用宏分类**：

| 类别 | 宏示例 | 说明 |
|------|--------|------|
| 角色信息 | `{{char}}`、`{{charName}}` | 当前角色名称 |
| 用户信息 | `{{user}}`、`{{userName}}` | 当前用户名称 |
| 时间信息 | `{{time}}`、`{{date}}`、`{{weekday}}` | 当前时间日期 |
| 系统信息 | `{{model}}`、`{{maxTokens}}` | 当前模型和配置 |
| 记忆信息 | `{{tableContent_N}}`、`{{memoryCount}}` | 记忆表格相关 |

宏替换的完整列表约 30 种，具体请参考宏系统文档。

## 自定义 INJ 规则

除了内置的多条 INJ，系统支持添加自定义规则。自定义规则需要指定：

1. 唯一的 name 标识
2. content 内容（支持宏）
3. autoMode 门控条件
4. depth 注入位置
5. role 消息角色

自定义规则与默认规则遵循相同的门控和注入逻辑。

## 调试建议

- **先看编辑面板的生效状态**：面板显示的生效/不生效和 AI 实际收到的是同一份后端裁决，不会有"面板说生效实际没注入"的两张皮
- 检查 INJ 是否生效：确认 enabled 为 true、autoMode 与当前模式匹配（拼错的 autoMode 会被静默拒绝注入）
- 检查平台限定：带 platform 字段的条目在网页对话不会注入
- 检查互斥冲突：-code 变体条目受 IDE 连接状态影响（CLI 不算 IDE 连接）
- 检查注入位置：确认 depth 值是否符合预期
- 检查宏替换：确认 `{{macro}}` 是否被正确替换（拼写错误的宏不会被替换，会原样保留）
- 想临时验证某条内容：用注入坞「⚡这轮」单次注入，跳过全部门控立即见效
- 完整的"为什么没生效"原因对照表见[注入系统概览](inj-overview.md)
