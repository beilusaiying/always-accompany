## 3.1 整体架构

### 3.1.1 收拢-发散-收拢三段式骨架 (Contraction-Divergence-Contraction, CDC)

P1 系统的宏观处理骨架为**三段式**：先收拢、再发散、再收拢。这一骨架来自设计者对人类思维节奏的观察及其形式化：刺激输入首先触发记忆检索的收拢（如"水"激活个体经验中的"溺水"，构成锚点），继而沿联想网络扩散至相关概念（"安全""游玩""划船"，对应扩散激活过程，Collins & Loftus, 1975），最终再次收拢为行动层面的方向判断。发散与收敛作为交替出现的独立认知环节，也是创造性认知研究中的经典二分（Mednick, 1962；Scaffolding Creativity, arXiv:2510.26490）。

三段的职能分别是：

1. **收拢（Contraction-1）**：括号信道分离 + 分词去噪 + 记忆召回，将用户输入从自然语言压缩为有意义的词集与上下文锚点。对应 Step-1、Node-0、Node-1。
2. **发散（Divergence）**：以锚点为基础进行两次发散——第一次经 SWOW 联想网络和 QKV 池交汇产出散词池，第二次经多路径（PPR、hop2、归因、类比、六度）产出信息词。对应 Node-2 至 Node-7。
3. **收拢（Contraction-2）**：以 Hough 式多对一投票将信息词收拢为方向词，经 BLQ 精排与红线剔除后产出最终输出。对应 Node-8 至 Node-10。其中 **Node-8** 是 BLQ 多维评分器在 transfer 内的历史编号：实现为 `calcBLQ` 函数（在 transfer 中以别名 `_calcBLQ_n8` 调用，环境变量 `P1_NODE8_BLQ` 门控、自 2026-05-31 起默认启用），承担方向词候选的多信号加性评分；Node-9 为 Hough 多对一选词；Node-10 为出口精排（`refineDirectionWords`）。

三段式在数据形态上表现为数据宽度先扩大后收缩：输入端是用户一句话（~10-50 字），发散中间态扩展至数十至上百个散词与信息词，输出端收拢为 15 个方向词术语注入主模型。

**规划中的 LLM 前置定位层与三线路架构**：LLM 在 P1 中的位置在设计上以多条并行线路刻画（设计者 2026-05-10 定义）：**线路 1** 为无 LLM 的纯词库线路，即本章描述的当前生产线路（完整度约 90%）；**线路 2** 将小型语言模型（Qwen3.5:2B）置于 SWOW 发散**之前**做前置定位——由小模型先对用户输入做语义定位（判断落在哪些轴/子轴方向），再交由词库管线执行发散；**线路 3** 将 LLM 置于 SWOW 发散**之后**做方向纠正与标注；**线路 C** 在前后两个位置均引入 LLM。线路 2/3/C 已在 lab 环境完整实装，尚未合入生产主线。该设计与"LLM-Free"定位不矛盾：生产主线（线路 1）的发散、投票、排序全程不依赖 LLM；LLM 环节仅承担定位/标注一职、不输出任何创造性内容，且为可选组件（离线时管线按线路 1 纯词库路径运行）。因此"LLM-Free"应理解为线路 1 的属性，而非设计中不存在 LLM 环节（另见微调指南与 v45 LoRA 8-Head 实验）。

### 3.1.2 管线完整调用顺序

`runPipeline` 是 P1 管线的唯一入口函数（Pipeline 模块），由上游 `getPromptHandler` 步骤 9 调用。管线内部按严格的串行顺序执行以下 12 个阶段：

| # | 阶段 | 调用代码 | 一句话说明 |
|---|------|----------|-----------|
| 0 | 热插拔检测 | `_checkHotReload(mode)` | 30 秒节流轮询 AT/TI 词库文件修改时间，mtime 变化则级联清除全部生产缓存 |
| 1 | 括号双信道 | `splitBracketChannels(inputText)` | 早于分词，将括号内真情绪分离为副信道，格式性括号豁免 |
| 2 | 主信道召回 | `callNode("recall", [mainText, ...])` | 串联 Node-1 分词 + Node-2 SWOW 发散 + Node-0 上下文/记忆锚点 |
| 3 | 副信道召回 | `callNode("recall", [sub, ...])` | 括号内容独立走一次 recallV2，散词池 Set union 合并（不取均值） |
| 4 | 六轴面发散 | `callNode("node3", [pool, ...])` | 散词池逐词经 8 来源定位 6 轴，每轴产出面词集 + 轴衰减（设计=一轴多信息点定位，见 3.2 节偏差说明） |
| 5 | 47 子轴定位 | `callNode("node4", [pool, ...])` | 4 路径探测器匹配 AT 术语坐标，产出激活子轴命中集（设计=沿各细分方向刻画语义变化率的方向细化定位，命中计数为降维实现，见 3.2 节） |
| 6 | 转接(信息池+投票+发散+选词) | `callNode("transfer", [...])` | 内含 Node-5 资源确认、Node-6 空间投票、Node-7 二次发散、Node-9 方向词选择 |
| 7 | BLQ 精排 | `refineDirectionWords(dwPool, ...)` | 高斯渐变衰减 + 断崖检测，筛除万金油与冗余 |
| 8 | 红线剔除 | `isRedlineWord(term)` | 四类红线正则硬匹配（路线词/诱导词/主观词/诊断词） |
| 9 | 输出组装 | `p1_act = top15`, `v5 = {...}` | 取 top15 term 为 p1_act，构建 v5 结构化输出与金字塔分层 |
| 10 | 白盒收集 | `getTrace()` / `clearTrace()` | 收集全链路白盒四问数据，pipeline 每轮读完即清 |
| 11 | 异步自学习 | `accumulateAxisStats` / `accumulateWordFreq` | fire-and-forget 写盘，不阻塞 return |

### 3.1.4 节点对接层与容错机制

管线中所有节点的调用均经过**节点对接层**（节点注册模块）的 `callNode` 函数包装。该层实现以下容错设计：

- **注册中心**：各节点文件通过 `registerNode("nodeX", fn)` 将自身实现挂载到全局注册表。
- **透明转发**：节点已注册且未抛错时，`callNode` 行为与直接函数调用完全一致（零开销）。
- **降级兜底**：节点未注册（模块尚未就绪）或节点抛出异常时，走 `fallback` 返回预设空值，异常不冒泡。
- **强制开关**：环境变量 `P1_NODES_OFF=node7,transfer` 可在运行时强制指定节点走兜底路径，用于故障隔离与单节点降级测试。

这一设计来源于多模块并行开发的工程需求。设计者确立的约束是：为全部并行开发的模块提供统一的注册与互调接点，使任一模块的故障或缺位不会级联阻塞整条管线。该约束对应容错工程中的故障隔离（fault isolation）与舱壁（bulkhead）模式，上述注册中心、透明转发、降级兜底、强制开关四项机制即其具体落地。

## 3.2 自然语言运行参照（伪代码）

本节以一个完整的输入示例，按管线实际执行顺序展开每个节点的处理过程。所有数据结构与阈值均来自真实代码。

### 示例输入

```
用户发了一句话："今天好累啊（真的好想休息）"
```

### Step -1: 括号双信道分离

```
管线启动，首先检查热插拔（30秒节流窗口内跳过）。
然后进入 Step -1，早于一切算法，早于分词。

splitBracketChannels("今天好累啊（真的好想休息）")
  // Step-1 括号提取模块

  1. 正则扫描所有括号对: PAREN_PATTERN = /[（(]([^（()）]+)[)）]/g
     命中 1 对: （真的好想休息）

  2. 豁免检查:
     - 纯数字序号 (1)(2)? 否
     - 单字母标号 (A)? 否
     - ps旁注? 否
     - 空/过短 (< 4字)? "真的好想休息" = 6字, 否
     → 判定: 真情感括号 → 进副信道

  3. 拆分:
     主信道 = "今天好累啊"        // 原文剥除真情感括号后的正文
     副信道 = "真的好想休息"      // 括号内容 = 真实内心想法
     hasBracket = true

  输出: { main: "今天好累啊", sub: "真的好想休息", hasBracket: true, bracketCount: 1 }
```

**设计动机**：设计者发现括号常承载正文未明说的真实情绪——正文说"没事"而括号里写"其实很难过"。若取均值则正负情绪互相抵消，故铁律规定**不取均值，保留张力**。

主副信道各自独立走一次 `recallV2`，两个散词池以 Set union 合并。

### Node-1: 分词与排噪（主信道）

```
recallV2 内部首先调用 Node-1 对主信道分词:

tokenizeNode1("今天好累啊")
  // Node-1 分词模块

  1. jieba-wasm HMM 分词:
     → ["今天", "好", "累", "啊"]

  2. 排噪三档:
     - "啊" → POS 虚词(y 语气词), HanLP+jieba 双词典交叉验证 → 硬排
     - "好" → BCC 频率查询 → 命中 DEGREE_WORDS 程度副词表 → 不排, 另存 intensifier
     - "今天" → BCC 频率 < 500000 → 保留, 权重 1.0
     - "累" → BCC 频率 < 500000 → 保留, 权重 1.0

  3. intensifier target 绑定:
     "好" (程度副词) → 向后找最近的进发散信息词 → 绑定 target = "累"
     → intensifiers: [{word: "好", target: "累", type: "degree"}]
     含义: "好累" 中的 "好" 加强 "累" 的权重，下游 Node-3 对 "累" 额外乘强化系数

  输出:
    words: ["今天", "累"]         // 去虚词后的实义词集
    wordWeights: { "今天": 1.0, "累": 1.0 }
    intensifiers: [{ word: "好", target: "累", type: "degree" }]
```

### Node-2: SWOW QKV 发散

```
divergeNode2(inputWords=["今天", "累"], isNoise)
  // Node-2 SWOW 发散模块

  1. 原词进池:
     swowPool = {"今天", "累"}
     // 注意: 本节点不存在"每词各查 topK 联想再并池"的路径——
     // 逐词独立 SWOW 发散兜底已于 2026-06-03 按红线"禁逐词发散"整段删除,
     // 发散只走下述 QKV 池交汇的整体操作

  2. NB300 质心计算:
     inputCentroid = mean(NB300["今天"], NB300["累"]) → L2 归一化
     // 285K 中文词 × 300 维 Numberbatch 向量
     // (原词全部无向量时可走 SWOW proxy 质心 fallback, 默认 off,
     //  该分支的联想词仅用于建质心, 不进池)

  3. QKV 池交汇 (inputVecs >= 2, 满足条件):
     Q = inputCentroid
     K = SWOW 全部 10,024 cue (swow_zh24_official.json) 的 NB 向量,
         与 Q 计算点积, 取 top3 cue
       → 假设命中 cue: ["疲劳", "辛苦", "精力"]
     V = 每个 top cue 再 swowDiverge 3 个联想词 (distance 门控过滤 cos>=0.85 近义)
       → "疲劳" → ["倦怠", "体力", "恢复"]
       → "辛苦" → ["付出", "坚持", "努力"]
       → "精力" → ["消耗", "充沛", "集中"]

  4. 出口排噪 (每个 cue/联想词进池前逐一判定 _isNonInfoN2):
     - 原词保护: "今天", "累" 不排
     - 程度副词豁免 (DEGREE_WORDS)
     - POS 虚词: isNoise 判定
     - BCC 超高频 > 800000: 若命中则排除
     - 停用词 4 份 union: 若命中则排除
     - 口语疑问补集: 若命中则排除

  散词池 swowPool (Set, ≈ 原词 + 3 cue + 9 联想词 ≈ 14词):
    {"今天", "累", "疲劳", "倦怠", "体力", "恢复",
     "辛苦", "付出", "坚持", "努力", "精力", "消耗", "充沛", "集中"}
```

**QKV 的设计定位说明**：设计上，"QKV 理解"被判定为需要 LLM 才能胜任的难点，是规划中 LLM 标注层（H5 LoRA）的核心职责——设计者确立的职责边界是：LLM 在 P1 中仅负责 QKV 理解、方向纠正与方向标注，不承担任何创造性内容生成；将其判定为难点的依据是人类语言逻辑的复杂性，使纯词表/向量方法难以完成深层语义解析。Node-2 此处以 NB 质心点积选 cue 的"QKV 池交汇"是无 LLM 线路（线路 1，见 3.1.1 节）下的系统层代理实现，不代表 QKV 理解问题已被 300 维向量点积解决。

### Node-0: 上下文召回

```
node0Recall(chatHistory, inputSwow, inputCentroid, ...)
  // Node-0 上下文召回模块

  1. 取最近 6 句上下文 (CTX_SENT_COUNT=6)
  2. 每句分词 → SWOW 发散 (每词 top4) → 与 inputSwow 交集打分
  3. NB cosine: 每句词质心与 inputCentroid 余弦
  4. combined = swowScore + (nbScore > 0.15 ? nbScore * 10 : 0)
  5. top4 句提关键词 → IPW 逆倾向加权排序

  假设上下文中有 "我最近加班很多":
    → 锚点: {node: "加班", strength: 0.45}
    → "加班" 加入 swowPool 参与定位 (权重 1.0 因为是上下文锚点)
```

### 副信道处理


### Node-3: 六轴面发散

**设计意图（先于实现说明）**：六轴定位的设计不是"一个轴给一个词一个数字"，而是**一个轴给一个词定位出多个信息点**——该词在此轴上关联到哪些概念、覆盖什么信息范围，定位结果再转移到词库，使一个词携带丰富的"信息 + 信息范围"进入后续环节。六轴承担的是**定位 + 细化 + 发散信息点**三重职能。这一"轴上定位产出为信息点集合而非标量"的设计与概念空间理论一致：概念在语义空间中占据的是区域而非点（Gardenfors, 2000），单一标量投影必然丢失区域结构。

**当前实现与设计的已知偏差**：现行代码将每词每轴压缩为单一标量分数（`allAxes[axis] = v`），faceByAxis 仅按标量降序取 top6——这是对设计的降维执行，丢失了"一轴多信息点"的信息结构，属于待重构项。下述流程描述的是当前代码行为，读者应注意它与设计意图的差距：

```
axis6(swowPool, mode="chat", inputWordSet, linguisticSignals, inputCentroid, intensifiers)

  1. 逐词 scoreWord(word, mode) — 查 8 来源算 6 轴分数:

       - VAD: 高唤醒 → psychology +0.08
       → allAxes: { psychology: 0.63, informatics: 0.2, sociology: 0.15, ... }

     "疲惫": allAxes: { psychology: 0.55, sociology: 0.10, ... }
     "压力": allAxes: { psychology: 0.48, sociology: 0.35, cognitive: 0.20, ... }
     "工作": allAxes: { sociology: 0.50, informatics: 0.15, ... }
     ...

  2. faceByAxis 构建 (每轴取 allAxes[axis]>0 的词, 降序 top6):
     psychology:  [{word:"累",v:0.63}, {word:"疲惫",v:0.55}, {word:"压力",v:0.48}, ...]
```

### Node-4: 47 子轴坐标命中

**设计定位**：47 子轴是 6 主轴定位的方向细化层——刻画一个词在 6 主轴粗定位内部沿各细分方向的语义变化率。6 主轴给出粗定位，47 子轴给出细化定位，两级定位再连接各类外部资源（SWOW / ConceptNet / Numberbatch / 词林 / CFN 等），整体构成"**6 轴 → 47 子轴 → 资源层**"的多层互联结构：词的激活按层级传导、加性汇聚，词在其中被逐级定位、细化、发散。

### Node-5 ~ Node-9: 转接器 (Transfer)

```
transfer(swowPool, mode, axisResult, inputCentroid, chatHistory, userCtx, intensifiers)
  // Transfer 模块

  ── Node-5: 资源确认 ──
  信息池 cleanInfoWords 构建:
    faceByAxis 各轴面词去重 → 每词查 AT 挂 axes_47/concepts/l1_summary
    坐标补充: AT原生 > node4激活 > 桥接预计算

  refineByResources(cleanInfoWords):
    3 通道确认:
      at_concepts: 共享 concept 簇确认
      cn_light: ConceptNet 关系边 1 跳
      cilin: 词林同小类
    → 产出: 每词挂 confirmCount (0-3) + relations[]
    → 不改坐标, 不投票, 不排序 (纯确认信号)

  ── Node-6: 空间投票 (主排名, 全链核心) ──
  spaceVote(cleanInfoWords, targets=AT_eligible):

    对每个靶(AT eligible术语) t, 每个信息词 i 投票:
      d = 1 - cosine(NB300[i], NB300[t])    // 语义距离
      idw = 1 / (1 + d^2 * 10)              // IDW, STEEPNESS=10
      vote(i→t) = w_i * idw                 // 加性票 (w_i=信息词权重)
      totalVote(t) = SUM_i(vote_{i→t})      // 累加, 无 /N

    温度分档:
      inputCount < 5 → T=1.5 (短句大圆, 多发散)
      inputCount > 10 → T=0.7 (长句小圆, 精确)
      else → T=1.0
    radius = 0.12 * T

    假设 "累"+"疲惫"+"压力" 共同对靶 "职业倦怠" 投票:
      totalVote("职业倦怠") = vote(累→职业倦怠) + vote(疲惫→职业倦怠) + vote(压力→职业倦怠)
      // 三票加性累积, 不除以3, 不连乘

    锚点提取: 多密度峰(按轴分组 + NoveltyBonus = 1/sqrt(count+1))
    域信号加分: domainBonus = 0.3 * topWeight (加性)

  ── Node-7: 二次发散 (5 路径) ──
  从 Node-6 锚点出发, 5 条路径产出额外信息词:

    1. PPR (PersonalizedPageRank):
       锚点 → KG seed → alpha=0.15, 15轮迭代 → 高分术语
       已在池: score += ppr * 5 * score (HDC 加性)
       新术语: 归一到 face 中位尺度

    2. hop2 (二跳扩展):
       锚点 concepts → CN关系词 → TI → AT术语
       gamma=0.75, 学科切换奖励(异轴1.0/同轴0.5)

    3. causal (归因发散):
       锚点 concepts → CN因果链 (Causes/HasProperty/CapableOf/MotivatedByGoal)

    4. analogy (类比发散):
       主轴锚点 NB → 其他轴 AT 术语
       倒U最优语义距离区间 cos [0.2, 0.7]
       ranked 模式, per-anchor cap 强制多样性

    5. sixDeg (六度路径):
       锚点 concepts → CN全关系 1-2跳 → SixDegreeBonus
       bonus = min(1.6, 1+0.2*(域数-1)), pathDecay<0.15 自停

  ── Node-9: Hough 多对一选词 (唯一出词路径) ──
  selectDirectionWords(cleanInfoWords, ...):

    每信息词 i 对 eligible 靶 t:
      cos47 = 47D_cosine(iw.axes_47, target.axes_47)    // >= VOTE_COS_FLOOR(0.15)
      relW = NB300_cosine(iw, target)                    // 语义相关度
      locW = 0.3 * cos47                                 // 定位入票
      vote = iwWeight * (relW + locW + domainW)          // 加性票
      totalVote(t) += vote                               // 累加器

    score(t) = totalVote * max(decay[target.axis], 0.15)
    加性质量门: score' = max(score * FLOOR, score - SUM(penalty_d))
      // 门3极性/门4 l1轴/门5 IDE/门7子串废词/门7b裸读可推/门9 low_search/门10 diagnostic-meta/门11 overfit

    金字塔分层: apex(核心) / mid(扩展) / base(擦边)

    假设产出 top20:
      [{term:"职业倦怠", score:2.8, axis:"psychology"},
       {term:"能量管理", score:2.1, axis:"cognitive"},
       {term:"社会支持", score:1.9, axis:"sociology"},
       {term:"压力应对", score:1.7, axis:"psychology"},
       ...]
```

### Node-10: BLQ 精排与红线剔除

```
refineDirectionWords(dwPool, {inputCentroid, nb, mode, inputWords, decay})
  // BLQ 模块

  1. 高斯渐变衰减:
     decay = max(0.15, exp(-(d - 0.45)^2 / (2 * 0.25^2)))
     // d = NB300 cosine distance, PEAK=0.45, SIGMA=0.25

  2. 断崖检测:
     若 前词score > 后词score * 3 (CLIFF_RATIO=3) 且序位 >= 5 (CLIFF_MIN=5)
     → 截断, 不强制填满 15 条
     // 防止低质量方向词被硬填进输出

  3. finalScore = node9Score * gaussDecay
     // 高斯衰减是"算位置非压分"的软定位, 不夺 Node-9 投票次序
```

**BLQ 融合方式的演化说明**：早期版本的 Node-10 曾存在 `min(factors)` 质量门（多因子取最弱值连乘进最终分，等价 AND 门），与系统确立的加性融合铁律（空间加性汇聚而非线性相乘、非硬匹配，对应 CombSUM 的 OR 门语义，Fox & Shaw, 1994）相悖——任一因子趋零则整分坍缩，正是"多轴共振奖励"（OR 逻辑）的反面。该 factors 层已于 2026-06-03 按红线整段删除（实测其为从不乘进打分的死代码，但白盒展示层仍将 `min(factors)` 显示为软降权因子，与实际打分行为不符）。现行 BLQ 的实际结构为两层：**内层**是 Node-8 `calcBLQ` 的多信号加权 CombSUM（spatial / BM25-TF 饱和 / pathHarmony / NB / spec / 资源确认六加分通道线性求和，减去各只一处的加性抑制扣分，不连乘不取均值）；**外层**是 Node-10 的 `node9Score × 高斯渐变衰减`（乘子为软定位而非质量门）。从"多因子乘积"到"加性 CombSUM"的演化依据即上述加性融合铁律及设计者对乘积式融合的明确纠正——乘积会使任一弱因子否决整体，与多信号互补的设计目标相悖。

```

```

```
{inputWords[], swowPool Set, inputCentroid Float32Array(300), anchors[], linguisticSignals, intensifiers[]}
  |  swowPool → array
  v
axis6(node3) → {wordProfiles[], faceByAxis:{axis:[{word,v,dimSignals}]}, axisDecay:{axis:float}, mainAxis}
  |  wordProfiles
  v
axis47(node4) → {activated:{subAxis:int}, witnesses:{subAxis:string[]}}
  |  faceByAxis + activated/witnesses + _inputWords
  v
transfer (node5+node6+node7+node9)
  |  node5: refineByResources → 每词挂 confirmCount/relations
  |  node6: spaceVote → fullVoteMap 回写 iw.score = totalVote
  |  node7: PPR/hop2/causal/analogy/sixDeg → 新词加入 cleanInfoWords
  |  node9: selectDirectionWords → directionWords top20
  v
node10: refineDirectionWords + isRedlineWord → 最终 p1_act top15
  v
{p1_act, v5, directionWords, pyramid, cleanInfoWords, trace, whitebox}
```

### 3.4.2 门控设计原则

环境变量门控遵循以下设计原则：

1. **默认全开（safe-on）**：绝大多数功能性开关默认开启，仅 `P1_DATA_RECALL`（实验阶段）和 `P1_PYRAMID`（可选特性）默认关闭。
2. **回退关闭（safe-off）**：设置 `P1_BRACKET=off` 即完全回退到纯单信道，与该节点上线前行为完全一致。
3. **无需重启**：所有环境变量在进程启动时读取一次，热插拔通过 mtime polling 实现动态刷新。
4. **节点级隔离**：`P1_NODES_OFF` 允许在不停服的前提下将单个节点降级为 fallback 空值输出。

### 3.4.3 热加载机制

P1 管线支持**运行时词库热加载**，不需要重启服务进程即可使新词库生效。机制如下：

```
热加载流程:
  ┌──────────────────────────────────────────────────────────┐
  │  每次 runPipeline 调用时:                                │
  │    1. 检查节流窗口: now - lastCheck < 30s? → 跳过       │
  │    2. stat() 读取当前 mode 的两个词库文件 mtime:         │
  │       - activation_terms_{mode}.json                     │
  │       - transfer_index_{mode}.json                       │
  │    3. 与上次记录的 mtime 对比:                           │
  │       - 首次记录: 建立基线, 不触发清缓存                │
  │       - mtime 变化: dirty = true                         │
  │    4. dirty → clearTransferCaches()                      │
  │       级联清除: transfer缓存 + axis缓存 + recall缓存    │
  │    5. 下次 getter 调用时自动重新加载新词库               │
  └──────────────────────────────────────────────────────────┘
```

**代码锚点**：`_checkHotReload` 函数（Pipeline 模块）

级联清缓存的传导链：`clearTransferCaches()`（Transfer 模块导出）内部调用 `clearAxisCaches()` + `clearRecallCaches()`，确保 transfer、axis、recall 三层缓存全部失效，新词库在下一次 `runPipeline` 调用时被自动加载。

**设计约束**：
- 轮询间隔默认 30 秒（`P1_HOT_RELOAD_INTERVAL`），每次仅 2 个 `fs.statSync` 系统调用，开销可忽略。
- `P1_HOT_RELOAD_INTERVAL=0` 可完全关闭热插拔。
- 热加载仅触发缓存清除，不修改现有缓存逻辑。

### 3.4.4 自学习写盘机制

管线每次运行完成后，异步（fire-and-forget）将以下数据写入 per-char 词库目录（`vocab/user/`），供 P9 离线整理与 P1 下次读取：

| 写入目标 | 调用函数 | 数据内容 | 用途 |
|----------|----------|----------|------|
| `axis_stats.json` | `accumulateAxisStats` | 本次六轴面聚合分数 | P9 校准轴权重 |
| `word_freq.json` | `accumulateWordFreq` | 用户输入词频 + 共现 | P1 SWOW 读取升权 |

**门控**：`P1_SELF_LEARN=off` 关闭。`userCtx` 缺失（test/lab 模式）时静默跳过。

**红线**：
- 写入以 `Promise.resolve().then(async () => {...})` 异步执行，不阻塞 `runPipeline` 返回。
- 写入失败整段 `try/catch` 静默，不冒泡不影响主流程。
- 不改动自学习模块算子本身的逻辑。
