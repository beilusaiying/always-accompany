# 记忆系统

always-accompany 的记忆不是一个搜索框，也不是把所有聊天记录放进向量库。它由几条职责不同的链组成：

- **记录与结构化**：把对话中的人物、事件、偏好、任务和状态写进可编辑表格或文件；
- **冷热分层与归档**：近期内容保持易用，较旧内容按层保存，原始资料不因为上下文清理而消失；
- **当前轮召回**：P1 从本轮线索寻找相关旧事；
- **明确触发**：世界书按关键词和规则注入固定背景；
- **可选语义检索**：beilu-vectordb 提供全文、向量或混合搜索；
- **可追溯消费**：回复可以展示“本轮运用记忆”，让用户看到哪些记录真正进入了回答。

这些能力可以单独使用。它们组合后的目标是：**保留足够完整的过去，但只把当前真正需要的部分交给 AI。**

## 你会感受到什么

### 长期信息不只依赖当前会话

角色相关的长期信息保存在用户 × 角色边界下。换一段对话时，系统不只依赖当前聊天窗口还剩多少原文。

### 不必把所有历史都塞进上下文

近期原文、结构化记忆、世界书和召回结果按不同用途进入提示词。清理上下文只是减少本轮发送内容，不等于删除磁盘上的原始记录。

### 可以纠正 AI 的记忆

记忆不是不可见的模型内部状态。用户可以查看表格、热层、归档与预设，修改错误内容后再验证后续召回。

### 可以知道它为什么想起这件事

后端把本轮召回记录随回复传给前端，消息下方可显示可折叠的“本轮运用记忆（N）”卡片。这不是完整的因果解释，但至少把实际消费的来源暴露给用户。

## 记忆数据放在哪里

角色记忆根目录由用户和角色共同确定，再在其下区分 Chat、Code、Work 等模式数据。

    data/users/<user>/chars/<character>/memory/
      ├─ tables.json / code_tables.json / work_tables.json
      ├─ tasks.json（同一角色卡内共享）
      ├─ hot / warm / cold 归档层
      ├─ code/
      │   ├─ active/
      │   ├─ archive/
      │   └─ projects/
      ├─ work/
      │   ├─ active/
      │   ├─ archive/
      │   ├─ outputs/
      │   └─ workflows/
      └─ _vector/
          └─ index.json

实际目录会随功能和迁移版本变化，管理时应以应用内记忆面板与当前代码为准。不要在不理解索引和归档关系时直接批量移动文件。

## P1：当前轮如何找回旧事

### 三种可选状态

每个模式的 P1 路由可以是：

| 路由 | 含义 | 当前声明默认 |
|---|---|---|
| 自驱动 P1（10） | 本地算法管线召回，不为每次召回调用 LLM | Chat、Code、Work |
| AI P1（01） | 旧的 AI 检索路线，作为互斥备选 | Smart、Bot |
| 关闭（00） | 本模式不运行 P1 | 用户可选 |

自驱动 P1 与 AI P1 最多启用一个，也可以全部关闭。除此之外还有插件级“启用 P1 召回”总闸；总闸关闭时，不应因为模式声明仍为开启就继续加载资源或执行召回。

用户可以在 P1 面板的“各模式 P1 路由”中修改选择，下一轮对话生效。

后端保留物理源缓存以节省重复加载，但本轮候选、输入、排名和注入结果必须保持 chatId 与窗口归属，不能把一个窗口的结果复用给另一个窗口。

### 当前资源与证据边界

2026-08-03 的一轮后端白盒记录中，中文命中请求约 560.9 ms；同日更晚的一轮完整进程树工作集峰值约 2054.5 MiB，严格 2 GiB 门禁未通过。

这些数字证明当前机器上的链路可以运行，也暴露了资源成本；它们不是稳定性能 benchmark。正式结论仍需要 cold、warm、P50、P95、多轮峰值内存，以及带 gold record 的 Recall@k、MRR、nDCG 和失败例。

因此：

- 不应再宣传“毫秒级”而不说明冷启动和统计口径；
- 不应把没有 gold labels 的内部样本写成“90% 召回率”；
- P1 适合愿意承担本地资源换取多线索召回的人，不是所有用户的强制默认。

完整技术说明见 [P1 当前运行架构](../p1-recall/ch7-current-runtime.md)。

## P2–P8：不要把设计表当成默认功能表

| 模块 | 预期职责 | 当前公开口径 |
|---|---|---|
| P2 | 归档内容的 AI 整理、命名与格式化 | 后台自动触发已停止；手动按钮已接到显式手动链，真实模型产物尚需单独验收 |
| P3–P6 | 更高层整理、反思、压缩与格式维护 | 默认不作为新用户运行路径；需逐项核对预设与触发器 |
| P7 | 上下文压缩 AI | 供手动/阈值压缩链选择；是否实际调用取决于配置与可用服务源 |
| P8 | 联网搜索相关预设 | 与联网能力有关，是否运行取决于启用、提示词和真实服务链 |

机械归档、表格迁移和 AI 总结是不同机制。机械归档成功，不代表 P2 的 AI 总结已经运行。

## 向量检索和 P1 是什么关系

beilu-vectordb 提供基于 Orama 的全文、向量和混合搜索。它默认关闭向量功能，需要配置 OpenAI 兼容 embedding 端点、模型和维度；记忆文本会发送给你配置的 embedding 服务。

它与自驱动 P1不是“新旧版本”关系：

| 路线 | 主要依据 | 更适合 |
|---|---|---|
| 世界书 | 明确关键词与固定内容 | 稳定规则、设定和必须注入的信息 |
| 全文检索 | 词面重合 | 名称、术语和原句线索 |
| 向量检索 | embedding 语义相似度 | 同义改写和语义邻近文本 |
| 自驱动 P1 | 直接词、概念关系、联想方向、时间与模式等组合 | 间接线索、关联回忆和多阶段收拢 |
| 大上下文 | 保留近期原文 | 连续对话和细节仍在窗口内的任务 |

最佳路线取决于任务。always-accompany 可以把这些方法组合，但目前还没有完成同一语料、同一 gold labels 下的外部对比，不能据此声称任何一条全面优于另一条。

向量配置与隐私边界见 [语义检索插件](../plugins/vectordb.md)。

## 它与常见记忆 / RAG 的差别

### 如果你只需要一个 SDK

通用记忆 SDK 通常更容易接入已有应用。always-accompany 更重，因为它同时提供角色、UI、模式、提示词、工具、安全和持久化。选择 always-accompany 的理由应该是你需要这套组合，而不是只要一个 API。

### 如果你已经有向量库

你可以继续使用语义检索思路。always-accompany 额外关心的是：谁写入、写到哪一层、哪种模式可以读取、何时归档、召回后如何注入、用户如何追溯和纠错。

### 如果你依赖大上下文

大上下文适合保留近期细节；分层记忆适合长期保存与按需取回。两者可以同时使用，不需要制造“只能选一个”的冲突。

### 如果你靠手写总结和世界书

它们依然是可控而有效的工具。always-accompany 把这些明确规则与自动召回放在一起，让固定设定、结构化事实和关联回忆各自承担不同职责。

## 管理记忆时的原则

1. **磁盘数据是真相源**：面板状态、缓存和向量索引都应能回到实际文件核对；
2. **角色与用户先隔离**：不要把不同用户或角色的目录当作同一池；
3. **模式分区与角色共享要分开**：Chat/Code/Work 的表与私有目录按模式划界，但 `hot/warm/cold` 和 `tasks.json` 在同一角色卡内共享；需要项目级硬隔离时使用不同角色卡；
4. **写入和召回分开验证**：写进去了不等于能被正确找回；
5. **归档和删除分开处理**：迁移到冷层不是丢弃；
6. **修改后看真实消费**：通过下一轮召回记录和输出验证，不只看保存成功提示。
