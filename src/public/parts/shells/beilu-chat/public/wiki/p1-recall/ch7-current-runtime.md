# 第7章 当前生产合同：注意力、上下文与缓存

> 本章是 2026-08-03 的当前运行态说明。第1–6章保留 P1 的设计理念、旧节点体系与历史实验；当历史章节里的“组件态”“AI P1 现役”或旧节点编号与本章冲突时，以本章和当前源码为准。

[繁體中文](../locales/zh-TW/p1-recall/ch7-current-runtime.md) · [English](../locales/en/p1-recall/ch7-current-runtime.md) · [日本語](../locales/ja/p1-recall/ch7-current-runtime.md)

## 7.1 当前模式

P1 有三个可用状态，两个召回器互斥：

| 状态 | 自驱动 P1 | AI P1 | 行为 |
|---|---:|---:|---|
| `00` | 关 | 关 | 不运行 P1 召回 |
| `10` | 开 | 关 | 本地 Node0–4 白盒召回；当前 Chat、Code、Work 的默认路由 |
| `01` | 关 | 开 | 保留原 P1AI 召回；当前 Smart、Bot 的路由 |

当前不开放 `11` 双开。宿主只裁决一个 owner，避免双跑、双注入和两个模块互相递归。若后续实验“自驱动 P1 先跑、结果经宏给 P1AI 再处理”，也应作为单向组合管线单独设计，不能把两个 owner 同时打开。

## 7.2 本轮注意力输入合同

自驱动 P1 的 Node0 输入严格区分三类单元：

```text
user_current：当前用户输入，固定 1 条
user_context：最近用户消息，最多 5 条，按时间从近到远取用
data：当前用户、角色与模式下的结构化 Data
ai_output：0 条，不把历史 AI 回复当作召回锚点
```

Data 在这里承担可编辑、可验证的长期上下文，不是额外附在 AI 历史后面的第四份重复材料。这个合同的目的，是让用户最新意图和用户维护的结构化事实主导注意力，减少旧 AI 措辞被系统反复自我强化。

“最近 5 条”只约束召回锚点，不等于主模型最终只能看到 5 条对话。主提示词仍可由宿主按窗口、模式、INJ、预设与上下文预算装配；P1 只负责决定长期材料中什么值得在本轮被重新看见。

## 7.3 Node0–4 白盒链

```text
Node0  输入编译
  ├─ 当前用户输入
  ├─ 最近 5 条用户上下文
  └─ Data
        ↓
Node1  分词、词性、有效锚点
  ├─ 中文与英文分词/POS
  ├─ 时间表达：年、月、日、202x/xx/xx 等
  └─ 专属名词与短语
        ↓
Node2  关联扩展
  └─ SWOW / ConceptNet / 词林 / ATOMIC / 领域词
        ↓
Node3  多证据审查
  └─ BLQ / NB300 / WordNet 等信号决定候选去留
        ↓
Node4  真实记录召回与排序
  ├─ Data + hot/warm/cold
  ├─ code/work 当前窗口对齐的 MD
  ├─ 精确短语、BM25、时间和文件创建时间
  └─ 层级、Top、pinned、importance、weighted/RRF
        ↓
recalledRecords + directionWords + trace
```

Node2 的联想不是记忆事实。候选必须在 Node3/Node4 回到真实记录层接受证据和排序，最终输出才可进入宿主上下文。

## 7.4 四个隔离维度

运行时路由需要同时携带：

1. **用户**：不同用户的数据不串线；
2. **角色卡**：同一用户的不同角色拥有不同记忆来源；
3. **chatId**：主要服务 code 多窗口的对话绑定与穿透；
4. **窗口/模式**：当前 code、work、chat 窗口的选择、短期状态和最终排序彼此独立。

这里要区分“持久化源”和“本轮可变状态”。为了节省内存，物理源缓存可按用户 × 角色 × 模式共享；chatId 和窗口不需要各复制一份完整文件缓存。但本轮候选、当前对话输入、最终排名和注入结果必须保留 chatId/窗口归属，不能从共享缓存直接复用。

## 7.5 Data、三层记忆与文件时间

- **Data**：结构化、用户可编辑的状态和长期事实，也是 P1 的输入与检索来源；
- **hot**：近期、高频、正在使用的材料；
- **warm**：阶段性归档材料；
- **cold**：长期历史，仍可按需被召回；
- **code/work MD**：按当前窗口和模式选择进入来源集合，不依赖 `data/` 目录保存唯一重要内容。

时间不是只从正文做字符串匹配。显式年月日、标准日期、记录时间和文件创建时间都可成为候选信号；时间查询中的匹配项会获得更高关注，但仍需与文本证据、层级和重要度共同排序，不能只凭“文件新”就压过真正相关记录。

Top 也不等于普通搜索的 `top_k`：它是一组能让材料重新靠近注意力的持久信号，包括 pinned/top、importance、recency、层级和历史命中。用户修改这些值后，来源版本会失效并重建索引。

## 7.6 P1 缓存合同

### 7.6.1 物理源缓存

`storage_read.mjs` 递归读取 JSON、JSONL、MD，并以文件 mtime、birthtime、size 生成版本签名。缓存命中时跳过磁盘读取和解析；文件发生变化时重建。LRU 默认/硬上限为 8 个作用域。

缓存键面向可共享的用户 × 角色 × 模式物理源，不复制 chatId/窗口可变状态。

### 7.6.2 分词与 POS 缓存

`node1_tokenize.mjs` 以完整文本和分词/POS 后端、资源身份组成键。只有通过完整合同校验的结果才能入缓存；失败、缺字段或半成品不缓存。读取和写入均复制对象，防止下游修改污染后续请求。默认容量 4096，硬上限 16384。

### 7.6.3 倒排索引缓存

`node4_rank.mjs` 只缓存纯 `docs → postings` 索引。版本会覆盖正文、元数据、文件时间、Top、importance 等影响排序的材料；变更后重建。候选集合、查询权重和最终窗口排名从不作为共享结果缓存。索引 LRU 硬上限为 8，文档分词缓存也有容量修剪。

### 7.6.4 资源与服务生命周期

- NB300 使用 `mmap_mode="r"`，避免一次性把完整向量矩阵复制进内存；
- tokenizer、ONNX POS 和可选资源按需加载；
- tokenize/vector/llmtok 三个 HTTP 服务常驻，不在每条消息上 spawn；
- warmup 使用 single-flight，同一时间只执行一次；
- 默认不因短暂空闲自动关闭，避免下一轮重新承担约 20 秒冷启动；需要时仍可配置空闲退出。

设计原则是：**共享稳定源，版本化中间产物，隔离本轮状态，失败不入缓存。**

## 7.7 主模型提示词缓存

P1 缓存减少检索侧重复计算；提示词缓存减少主模型侧稳定前缀的重复计费，两者不能混为一谈。

在 Anthropic 兼容路径中：

- 第一断点位于稳定 system 区；
- 第二断点位于动态 Data、after-chat 等易变尾部之前；
- 旧工具结果会按累计体积动态压缩，保留最近的完整细节；
- 默认低于 200k token 时阻止 AI 随意执行 `<contextClean>`，以免频繁改写稳定前缀；
- 用户原始消息受保护，清理默认是可恢复隐藏，永久删除需显式执行。

只有支持相应 prompt caching 的供应商路径才应用这些缓存断点；其他模型不能沿用同样的收益口径。

## 7.8 白盒与 Bug 提醒

一次可交付的 P1 运行记录至少应显示：

- 原始输入有没有进入 Node0，中文是否保持 UTF-8；
- `user_current/user_context/data/ai_output` 各有多少单元；
- Node1 是否真的产生 token、POS、时间与专名锚点；
- Node2/3 每类候选进入、删除与失败原因；
- Node4 扫描文档数、索引 cache hit/rebuilt、排名信号与最终来源；
- 模型/资源/HTTP/超时/内存错误必须明确报告，不能静默变成“0 条召回”。

P9 反馈使用 `p1_feedback_v1` 结构化包记录 trace、候选、命中、耗时和用户反馈。P9/CLI 可以据此做词库维护或后期微调，但不得仅凭一次用户“没召回”就自动把词写进全局词库；必须保留来源、作用域、建议改动和人工确认。

## 7.9 当前实测边界

2026-08-03 当前机器的后端白盒记录：中文命中请求约 `560.9 ms`，扫描 71 份文档、返回 1 条；首次无命中请求约 `1157 ms`。内存方面，同日更晚一轮实测的完整进程树工作集峰值约 `2054.5 MiB`——超出 2048 MiB 的严格验收门禁约 6.5 MiB（约 0.32%），严格 2 GiB 验收为未通过（此前一轮记录为 1.72 GB，已被该次实测取代）。

这证明当前后端传导和中文链路能跑通，但不是稳定性能基准。正式发布前仍需多轮报告 cold、warm、P50、P95、内存峰值，以及带 gold record 的 Recall@k、MRR、nDCG 和失败例。现阶段不得把历史无 gold 的四模式样本写成“召回 90%”。

## 7.10 与团队记忆产品的定位差异

TencentDB Agent Memory 也有上下文预算与缓存设计：L2/L3 直接注入、L0/L1 工具化读取，以 Fixed Binding 和 ACL 限域；MemoryProxy 缓存 session、injection 和 skill 状态，并要求多节点共享存储以避免上游 KV cache miss。

北麓不应宣称对方“没有上下文/缓存”。更准确的区别是：TencentDB 主要管理 Agent 可携带的团队记忆资产，北麓主要在长期对话的每一轮编译模型应该注意什么、按什么证据排序、放到提示词哪里，并通过有界缓存复用稳定计算而不冻结动态注意力。
